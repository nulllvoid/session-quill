# ADR 0022 — An always-on dashboard, and runs that report their own timings

Date: 2026-10-11 · Status: accepted · Builds on [ADR 0013](0013-recipe-context-and-reply-contract.md) and [ADR 0017](0017-run-access-levels.md)

## Context

The dashboard was easy to lose. Every worker start picked a random port, so a bookmark or an open tab broke on the next restart. The owner session lived only in the worker's memory, so a restart also signed the browser out, and a signed-out browser saw a JSON error rather than instructions. Nothing showed the address once the first link was used. Getting the worker to start at login meant a hand-made Task Scheduler task or systemd unit.

Two smaller gaps sat on the agent side. A fix run (`edit_source`) skipped the self-check when its recipe did not ask for it. Nobody could say where a run's time went: queueing, creating the worktree or the agent itself. The orchestration plan wants that measured before it optimises anything.

## Decision

- **Stable port.** `ui_port` defaults to `47321`. The server tries it first. If the port is taken (`EADDRINUSE`) or reserved by the OS (`EACCES`), it falls back to a random port and logs that, so a busy port never stops the worker. `ui_port = 0` keeps the random port. `state/ui-endpoint.json` still records host, port and pid, plus `configured_port` when the server fell back; `quill ui` then prints a warning and the status line ends with "⚠ port 47321 taken; using N". Readers of the file accept only a loopback host and an integer port from 1 to 65535 before building a URL or the status line's OSC 8 sequence.
- **Upgrading configs.** Earlier releases saved every default, so their `config.toml` holds `ui_port = 0` without anyone choosing it. The user config now carries `config_version = 1`. On the first load of a file without it, a stored `ui_port = 0` is dropped (the fixed port applies) and the marker is written; a `ui_port = 0` set after that is kept. A save no longer writes `ui_port` while it is the untouched default, so a later release can move the default.
- **Durable sign-in.** Owner sessions are stored in `state/ui-sessions.json` as SHA-256 hashes with an expiry. A session lasts 7 days and is renewed on use (sliding). A renewal is written at most once an hour per session, so polling does not rewrite the file. Expired entries are pruned on load and on use. The plain token exists only in the browser's HttpOnly cookie, which has `Max-Age` equal to the 7-day session and is re-sent on every authenticated response, so the browser keeps it exactly as long as the session slides. The CSRF token is an HMAC keyed by the session token, compared in constant time, so it is as unguessable as the cookie and an open page keeps working across a restart.
- **Revocation.** `quill ui --revoke` deletes the stored hashes and every outstanding one-use secret, and always writes `control/ui-revoke.json`. A running worker drops the sessions it holds in memory and deletes the file on its next tick; a stopped worker does so when it starts. While the file exists the worker verifies no session and writes none back, so a session renewed between the command and the tick cannot be re-saved. The command waits up to 5 s only when a worker is running; if it does not confirm in time, the file stays and the command says the sign-out applies on the next tick or start.
- **Sign-in page.** A request for the dashboard page (`/` or any `.html` under `/ui/`) without a valid session gets a 401 HTML page. It tells the reader to run `/session-quill:ui`, or `quill ui` from a terminal. It uses the dashboard stylesheet and tokens and has no script and no data. Scripts, styles and fonts stay public because they hold no data. The `/v1` API keeps its JSON errors.
- **Status line link.** `quill status --statusline` appends the dashboard base URL as an OSC 8 hyperlink. It does so only when `ui-endpoint.json` names the pid of the worker whose heartbeat is healthy. A stopped worker or a stale file prints nothing. The link never carries a secret: opening it lands on the sign-in page, or on the dashboard if the browser is already signed in.
- **`quill worker install` / `uninstall`.** Install registers a per-user login entry that runs `quill worker start` once. It needs no administrator rights:
  - Windows: a Task Scheduler task named `Session Quill worker (quill)` with a logon trigger for the current user and an interactive token. It is registered from a generated XML file with `schtasks /Create /XML … /F`. The task runs `wscript.exe` on a generated `worker-login.vbs`, which starts node without a console window. Both generated files are written as UTF-16LE with a BOM, so a profile path outside ASCII survives (wscript reads a BOM-less script in the ANSI code page).
  - macOS: a LaunchAgent at `~/Library/LaunchAgents/com.session-quill.worker.plist` with `RunAtLoad` true and `KeepAlive` false, loaded with `launchctl bootstrap`.
  - Linux: a `Type=oneshot` systemd user unit with no `Restart=`, enabled with `systemctl --user enable`. Values are quoted for systemd: `%` is doubled in `Environment=` and `ExecStart=`, and `$` is doubled in `ExecStart=` (`Environment=` does no variable expansion).

  A custom `QUILL_HOME` is passed to the entry. On macOS and Linux the entry also carries the `PATH` from install time (`EnvironmentVariables`, `Environment=`), because launchd and systemd start login entries with a minimal `PATH` in which `claude`, git or a version-managed node may not resolve; reinstall after moving them. Installing twice leaves one entry: `/F` replaces the task, `bootout` runs before `bootstrap`, and `enable` is idempotent. Uninstalling when nothing is installed succeeds and changes nothing. Install writes `state/autostart.json`. The snapshot's `meta.worker_autostart` reads only that marker (plus the plist or unit file where there is one), so the worker never spawns an OS tool for it. `quill doctor` also asks Task Scheduler (`schtasks /Query /TN …`) on Windows, where there is no entry file, and reports "marker present but task missing" when the task was deleted outside Quill. Crash restarts stay with `ensureReady`'s rate-limited backoff in the hooks, not with OS keep-alive. Every OS call goes through an injectable runner, so the tests use fakes.
- **Mandatory self-check.** A run whose permissions include `edit_source` always gets the read-only self-check turn of ADR 0013, whatever its recipe's `self_check` says. When the turn cannot run (the agent reported an error, the reply has no session id to resume, the reply still breaks its contract, the run was stopped, or less than a minute is left before the deadline) or does not finish cleanly, `result_quality.self_check_skipped` records why.
- **Run timings.** A run records `timings`. `queue_wait_ms` runs from the request to dispatch on the worker clock. `worktree_ms` is the time to create the checkout and is present only when one was created. `agent_ms` covers the agent process from spawn to its last turn, including repair and self-check. Only fields that were measured are written, and a run that fails keeps what was measured before it failed (queue wait from dispatch on, setup time even when the checkout fails, agent time when the runtime cannot be spawned); there is no `test_ms` until there is a worker test gate. The timings travel through `handoff-tx` like other handoff fields. The dashboard shows them on each run ("Queue wait 2.0 s · Setup 850 ms · Agent 1 min 35 s") and `quill handoff list` prints them.
- **Dashboard.** The top-bar address gets a copy button through the existing `data-copy` handler. When a login entry is installed, the worker health item opens a popover saying "Starts at login". The item still reads "Worker: connected".

## Consequences

- A bookmark to `http://127.0.0.1:47321/` survives restarts and reboots, unless another program holds the port, in which case `quill ui` and the status line show the fallback address.
- **Port squatting.** The cookie is not bound to a port (browsers scope cookies by host only), and a fixed, well-known port is easy to target. A local program that takes 47321 before the worker starts receives the browser's requests to that address, including the `st_owner` cookie, and could replay it against the real worker on its fallback port; it could also serve a look-alike page. `SameSite=Strict` and the loopback host and origin checks do not stop a process that is already on this machine as the same user. We accept this because such a program can already read the state directory, the store and the browser profile, so the cookie gives it nothing new; the fallback warning in `quill ui` and the status line makes the takeover visible, and `quill ui --revoke` ends every session. Machines shared with untrusted local users should set `ui_port = 0`.
- Anyone who can read the state directory can see which sessions exist and when they expire, but cannot sign in with that. They could already read the store.
- Signing out every browser is a deliberate step (`quill ui --revoke`); otherwise a browser idle for more than 7 days has to sign in again.
- Fix runs cost one more short turn when their recipe did not already self-check.
- The decision on worktree reuse can now rest on measured `worktree_ms`, not guesses.

## Alternatives considered

- **A prewarmed worktree pool.** Rejected for now. A pool adds cleanup, staleness and disk cost, and we have no measurement showing worktree creation matters. `worktree_ms` provides that measurement; recycling stays deferred until it shows a real cost.
- **A shared secret in a `ui.lock` file** that the browser or status line could present. Rejected: it would put a plain secret on disk and, through the status line, on screen. Hashed sessions plus a one-use link keep every plain secret in memory or in the HttpOnly cookie.
- **A separate always-on dashboard daemon.** Rejected: it would be a second process to own the store, with its own lifecycle and lock. The worker already serves the dashboard and owns the store. Starting it at login makes it always on without a second owner.
- **OS keep-alive** (`KeepAlive`, `Restart=always`, a repeating task). Rejected: a worker that crashes on start would loop. `ensureReady` already restarts with backoff and respects `quill worker stop`, which an OS keep-alive would ignore.
