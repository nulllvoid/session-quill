Recipe authoring

A recipe is a Markdown file with frontmatter and a prompt. The frontmatter is a ceiling on what a run may do; the worker decides the rest.

Where recipes live

LocationScopePrecedence
.quill/agents/The repository, shared with the teamHighest for that repository
~/.claude/quill/agents/Just you, including installed recipesPersonal
recipes/ (plugin)Built in: analyse, analyse-followups, attempt-fix, deploy-check, standup, file-task, workspace-setupLowest

Install someone else's recipes from a Git repository or a folder. The first command shows what each recipe may do and installs nothing; --confirm installs and records where each came from.

quill agent install https://github.com/acme/quill-recipes --ref v1.2
quill agent install https://github.com/acme/quill-recipes --ref v1.2 --only triage --confirm
quill agent uninstall triage

Frontmatter

---
name: deploy-check
description: Check whether each merged PR reached each environment
mode: analyse                      # analyse | analyse-followups | attempt-fix
permissions: { read_source: true } # the most a run may get
tools: [Read, Grep, "Bash(git log:*)"]
timeout_min: 10
inputs: [ticket, prs, deployments, work]   # also notes, related, history; omit for all
outputs: [summary, deploy_evidence, next_action]
self_check: true
---
For {{ticket.key}} ({{ticket.url}}): for each merged PR {{prs}}, find the deployment evidence...
FieldMeaning
nameThe recipe's id. A repository recipe with the same name as a built-in replaces it for that repository.
modeWhich reply contract applies: analyse (summary, next action, blocker), analyse-followups (plus child tickets, each with a description) or attempt-fix (plus test results and changed files).
permissionsread_source, edit_source, commit, push_branch, open_draft_pr. A ceiling: the run dialog shows them and anything with a side effect stays off until you tick it. Scheduled runs only ever read.
toolsNarrows the tool allow-list; it can never widen the permissions. Read-only analyse runs may use Claude Code subagents to split a large analysis by module and merge the results.
timeout_minThe run's own time cap.
inputsWhat the prompt may see: ticket, notes (your Notes section), prs, deployments, work (files, commits and, with source access, their diff), related (parent, siblings, children), history (earlier runs and how their suggestions were decided).
outputsThe typed fields the reply must return. Results from your own recipes arrive as suggestions on the ticket: accept or dismiss each one.
self_checkVerify each claim against its source in a read-only follow-up turn. From 1.0 this is always on for any run with edit_source, whatever the file says.

A recipe edited after a run was queued fails that run instead of running unreviewed.

The reply contract

Every run follows a stated method and evidence rule. Its reply adds confidence and sources, shown on the run in ticket detail. A reply that breaks the output contract gets one repair turn in the same session. A follow-up child ticket must carry a description in the Goal / Context / Done when format; a description output fills a missing ticket description and never replaces a valid one.

Access levels

Runs use your own Claude Code settings by default: your permission rules and connected MCP servers apply, and anything that would need your approval is refused, since nobody is there to answer. Commit, push and draft PRs still need their own checkbox. Full access (--access full) skips every permission check for one run; it is never the default and never scheduled. Schedules and file-task use Quill's narrow standard profile.

The worktree

An attempt-fix run gets git worktree add --detach at the ticket's recorded base commit, under Quill's own directory, never your working directory. Push and draft-PR rights exist only as provider tokens the agent's environment is given when you grant them. Each run records queue_wait_ms, worktree_ms, agent_ms and, when a test gate ran, test_ms, visible on the run and in quill handoff show.

There is no pre-warmed worktree pool. Recycling is deferred until the recorded timings show worktree creation matters; the decision is written down as an ADR either way.

The test gate

With test_command set on the repository, the worker runs it in the run's worktree after any run with edit_source finishes with a diff. No stdin, a timeout (test_timeout_ms, default ten minutes), and the exit code, duration and the last 4 KB of output recorded on the run:

test_gate: { status: "passed" | "failed" | "timeout" | "skipped", exit_code, ms, tail }
  1. Passed. The run's chip reads Tests passed (worker), and only then do PR bodies and suggestion text say so.
  2. Failed. The worker resumes the agent once with the failing output, then runs the gate again.
  3. Failed again. No suggestion is surfaced; the run records why.
  4. No test command. status: "skipped", and the run dialog says fixes are not test-verified.
The test command is repository code running under your user account. Granting edit_source is granting that.

Concurrency

[handoff]
max_concurrent_readonly = 2     # analyse, deploy-check, standup
max_concurrent_fix      = 1     # anything with edit_source

Read-only runs and source-editing runs are counted separately. Fixes on one repository stay serialised whatever the cap says, and the bulk handoff form shows waits for repo for the ones that will queue.

Batches and proposals

A handoff request may carry a batch_id (up to 64 characters). The dashboard's bulk action bar uses one per selection so a batch has a progress strip and a Cancel batch that cancels every queued run in it; quill handoff cancel --batch <id> does the same from the CLI.

A Run agent edit on a two-way artifact page becomes a proposed run on the ticket, with a deterministic id so repeated reconciles create exactly one. It runs when you approve it on the dashboard or with quill approve --run <id>. Nothing is ever queued without you: page editors are identified only by data the page itself carries, so there is no auto-approval.

quill agent run deploy-check PROJ-123
