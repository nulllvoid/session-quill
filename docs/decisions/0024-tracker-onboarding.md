# ADR 0024 — Onboarding from the tracker: import, repository resolver, clone with consent

Date: 2026-10-11 · Status: accepted · Builds on [ADR 0011](0011-tracker-sync-and-two-way.md), [ADR 0016](0016-done-when-check.md), [ADR 0018](0018-tracker-write-back.md), [ADR 0021](0021-pr-closes-its-tickets.md), [ADR 0022](0022-always-on-dashboard.md) and [ADR 0023](0023-bulk-runs-and-test-gate.md)

## Context

A new user starts with an empty board while their tracker already lists the work assigned to them. Each ticket then needs a repository before a run can read or fix code, and a ticket from the tracker usually names a project, component or link rather than a folder on this computer. Typing `quill ticket create` and `quill ticket set --repo` for each issue is the friction the orchestration PRD set out to remove.

The PRD drafts proposed three mechanisms that the review replaced:

- an **agent that clones** the repository it thinks the ticket needs, as part of resolving it;
- a new **`set-tag` request kind** so the dashboard could set any tag, including reserved `quill/` ones;
- a **per-ticket `repo add`**, registering a folder for one ticket at a time from ticket data.

## Decision

- **Import is opt-in and read-only.** `[tracker] import_assigned = true` in the user config makes the `tracker-sync` job list the open issues assigned to the token's user before it syncs: Jira `assignee = currentUser() AND statusCategory != Done` (through `/rest/api/2/search/jql`, falling back to `/rest/api/2/search` on sites without it), GitHub `is:issue is:open assignee:@me` in the configured `tracker.repo` through the search API. At most 50 per run. Each issue the store does not have becomes a ticket through the ordinary `ticket-create` event, under its tracker key, in the default project, with no repository, with the remote data already recorded and the id `externalTicketId(store, key)`. The event's source identity is `tracker-import:<KEY>`, so the worker and `quill tracker import` can both import an issue and it becomes one ticket. A key already present in any case, or as an alias, is skipped. GitHub issue numbers become `<PREFIX>-<n>`, the prefix being the tracker's first `prefixes` entry or the repository name in capitals. `quill init --bootstrap-from-tracker` turns the setting on, adds a `tracker-sync` schedule every 6 hours when none exists (writing the reconcile default too, since a first `[[schedule]]` replaces it), and imports once, listing what it imported. A worker that is not running gets the events in ingress.
- **The repository resolver is rules, not an agent.** With an import or a `[tracker.repo_map]` configured, each `tracker-sync` run resolves up to 25 open tracker-linked tickets that have no repository and are not tagged `quill/no-code`, least recently checked first. The first rule that matches wins:
  1. `[tracker.repo_map]`: the issue's Jira component (`"PROJ/Payments"`), then its project (`PROJ`), or the GitHub repository (`"acme/web"`), mapped to a registered repository id or to a remote address.
  2. A registered repository whose `git remote get-url origin` is a repository the issue links to: a GitHub issue's own repository, or a Jira remote link on a `clone_hosts` forge (a pull request, commit or file page names its repository in its path; GitLab's `/-/` separator is honoured). Jira's development panel is an internal API and is not read.
  3. A clone of that remote already on disk, in `auto_clone_dir` or beside a registered repository (hidden folders are skipped).
  Remotes compare as `host/owner/repo` in lower case, so `https://github.com/Acme/App.git` and `git@github.com:acme/app` match. The outcome is `linked` (the ticket gets the repository through a `ticket-update` with source `resolver`), `needs-clone` (a remote and, under rule 3, the folder of an existing clone to register) or `none`. Outcomes are journaled in the `tracker-sync` event as `resolutions` and recorded as `repo_resolution` beside the ticket without a revision bump; a timeline entry is added only when the outcome changes. For Jira the resolver reads the issue's project, components and remote links (two GETs per unresolved ticket). It never clones, never writes config and never runs an agent.
- **Cloning needs the owner's consent.** A `needs-clone` ticket shows **Needs clone** with **Clone…** on its card and in detail. `quill repo clone <KEY>` prints the remote, the host check and the target folder and clones nothing; `--confirm` clones, registers the folder in `config.toml` like `quill repo add` and links the ticket. `--url` names the remote instead of the resolver's. The dashboard dialog shows the same three facts and sends a `repo-clone` request that names the exact remote shown; the worker's onboarding extension runs such requests one at a time, plans again against the current config and disk, and links the ticket. While it runs the card shows **Cloning**. The worker re-reads `config.toml` at once after registering, and the CLI leaves a `reload-config.json` control marker so the worker knows the new repository before it applies the link.
- **What may be cloned.** Only `https://` and `ssh` (`ssh://` or `git@host:owner/repo.git`) remotes whose host is in `[tracker] clone_hosts` (default `github.com`, `gitlab.com`, `bitbucket.org`). Refused: credentials in the address (a password, or a user in an https address), `file:` and every `transport::address` form such as `ext::`, `http://` and `git://`, anything starting with `-` (option injection such as `--upload-pack`), path parts starting with `-` or equal to `..`, shell characters, and paths with fewer than two parts. The clone runs `git -c protocol.file.allow=never -c protocol.ext.allow=never -c submodule.recurse=false clone --no-recurse-submodules -- <remote> <folder>` with `GIT_ALLOW_PROTOCOL=https:ssh`, `GIT_TERMINAL_PROMPT=0` and a 10-minute limit, using the owner's own git credentials. The folder is the repository name made safe (letters, digits, `.`, `_`, `-`; no reserved Windows names), or `owner-name` when that is taken, and must sit directly inside `auto_clone_dir` (default `~/quill-repos`). The clone is made under a hidden `.name.partial-*` folder and renamed into place when complete, so an interrupted clone is never mistaken for a repository; a failed one is removed. A remote that already has a clone, registered or on disk, is never cloned again: it is linked or registered instead. Nothing runs inside the cloned repository.
- **The host allowlist is the owner's.** `clone_hosts`, `auto_clone_dir`, `import_assigned` and `repo_map` are read only from the user's `config.toml`. A repository's `.quill.toml` cannot set them, and they do not turn on key recognition. The dashboard request is checked against `clone_hosts` when it is submitted (except to register a clone already on disk) and again by the worker before it clones.
- **`quill/no-code`.** The `quill/` tag prefix stays reserved, with one exception the owner may set and clear: `quill/no-code`, through `ticket-update` fields `no_code` (boolean) or `tags`. `quill ticket set <KEY> --no-code yes|no` sets it. Such tickets show **No code**, are skipped by the resolver and cannot be cloned for. No new event kind.
- **A fallback that only suggests.** The built-in `workspace-setup` recipe has no permissions, reads only ticket data and suggests a repository, the `repo_map` line that would find it and one command to run. The owner runs it on a ticket; `tracker-sync` never does.

## Consequences

- A new user can go from an empty store to a board of their assigned issues, each linked to its repository or showing what to clone, with one command and one confirmation per repository.
- Tracker-sync costs one search request per run for the import and up to two requests per unresolved Jira ticket for resolution; resolution is capped at 25 tickets per run.
- The worker now writes `config.toml` (to register a confirmed clone). It uses the same writer as `quill repo add`, which keeps comments at the top of the file and rewrites the rest.
- Imported tickets have no description until someone writes one; the Description check (ADR 0014) flags them like any ticket created from a key.
- A repository on a host outside the defaults (a self-hosted GitLab) needs that host in `clone_hosts` before its links count as repositories or it can be cloned.
- Linear issues are not imported and Linear tickets are not resolved: Linear's assignment and attachment model needs its own mapping, left for later.

## Alternatives considered

- **An agent that clones** (the drafts' approach). Rejected: cloning from ticket data is a trust boundary, since a tracker issue can be edited by people the owner does not control. An agent deciding what to clone and where puts that decision with the least trusted input. Rules are predictable, testable and explainable in the preview; the agent's useful part, guessing when rules fail, survives as the read-only `workspace-setup` suggestion.
- **A `set-tag` request kind** for any tag. Rejected: it would reopen every reserved `quill/` tag to the dashboard and to two-way page edits, where today the reducer derives them. Only one owner tag is needed, so `quill/no-code` is allowed through the existing `ticket-update` path.
- **Per-ticket `repo add`** from ticket data. Rejected: repositories are registered once per folder in the user config and shared by every ticket; registering per ticket would duplicate entries and let ticket data name a folder. A confirmed clone is registered exactly like `quill repo add`, and every later ticket on that remote links to it.
- **Cloning automatically for mapped remotes.** Rejected: even a remote from the owner's own `repo_map` costs disk, time and network, and the review asked for consent at this boundary. The preview makes each clone one keystroke.
- **Resolving in the projection on every generation.** Rejected: it would run git for every ticket every two seconds. Resolution runs with `tracker-sync` and its result is journaled.
